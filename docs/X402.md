# x402 Payments

Machine payments for paid data access, using the x402 v1 shape
(`exactInEvm` scheme, EIP-3009 transfer-with-authorization payloads).
**This phase ships the guard only, wired to a deterministic mock
facilitator.** No keys, no network, no API credentials, no live
facilitator.

## What the guard verifies

Every payment attempt passes ALL of these checks (fail closed, typed
rejection codes):

1. **Schema**: requirement and payload validate against strict x402 v1
   schemas (`X402PaymentRequirement`, `X402PaymentPayload`, in
   `packages/contracts`). Unknown keys, wrong schemes, or non-v1 versions
   are rejected (`unsupported-x402-version`, `unsupported-scheme`).
2. **Network**: the requirement's chain id must be in the supported map
   (Base 8453, Ethereum 1) — `unsupported-chain`.
3. **Asset**: the contract address must be in the asset allowlist
   (fixture USDC entries) — `asset-not-allowed`.
4. **Recipient**: `payTo` must be in the recipient allowlist —
   `recipient-not-allowed`. Payments to arbitrary addresses never record.
5. **Amount**: positive, at or under the single-payment cap, and the
   payload's `value` must EQUAL the requirement's `maxAmountRequired` —
   `invalid-amount` / `amount-mismatch`.
6. **Expiry window**: `validBefore` after `validAfter`, and `now` inside
   the window — `requirement-expired`, `payment-window-invalid`.
7. **Replay resistance**: the EIP-3009 nonce must be globally unique
   (`payment-replay`); the facilitator also refuses to settle a seen nonce.
8. **Spend caps**: per-agent daily caps in USD cents
   (`spend-cap-exceeded`). Recorded payments RESERVE cap space; settled
   payments COMMIT it; rejected payments release it.

## Settlement evidence

Settlement is separate from verification: `verifySettlement` accepts
evidence only from **allowlisted facilitator ids**. It checks the
facilitator id, the `success` flag, the transaction hash, and the
network/chain binding against the recorded requirement. Failures:
`settlement-facilitator-not-allowed`, `facilitator-error`,
`settlement-mismatch`, `settlement-invalid`.

## Idempotency and reconciliation

- The same `paymentId` processed twice returns the SAME record; no second
  row is written and no cap space is double-counted.
- `reconcile()` reports settled-without-evidence records and duplicate
  nonces; the orchestrator exposes it on `GET /api/v1/payments`.

## Payments cannot grant trading authority

This is structural, not a rule: `PaymentRecord.grants` hard-codes
`trading: false` at every construction site, and the payments package has
no import path into the execution stack. A settled payment grants
content access only. Rejected payments grant nothing at all.

## API (orchestrator service)

| Method | Path | Semantics |
|---|---|---|
| GET | `/api/v1/payments` | records + reconciliation report |
| POST | `/api/v1/payments/verify` | process an attempt (idempotent by paymentId); 422 with typed code on rejection |
| POST | `/api/v1/payments/settle` | submit settlement evidence for a recorded payment |

## Limitations (explicit)

- Only the deterministic `MockFacilitator` is wired in. Enabling a live
  x402 facilitator requires: documented protocol-version compatibility, an
  ADR, an allowlist update, and a config flag. A payment itself can never
  change facilitator configuration.
- Signature bytes are treated as opaque evidence in this phase; real
  EIP-3009 signature recovery (ECDSA `recover` against `from`) is NOT
  implemented and is a prerequisite for any live facilitator work
  (see `docs/LIMITATIONS.md`).
- Records and reservations are in-memory; persistence requires a migration
  and an ADR.

## Verification

`packages/payments` ships 18 tests covering: happy path, idempotency,
unsupported chain/asset/recipient, amount mismatch, expiry, nonce replay,
spend caps, unregistered facilitators, wrong-chain evidence, failed
settlements, reconciliation, and the trading-grant structural invariant.
